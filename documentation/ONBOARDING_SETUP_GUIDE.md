# Onboarding — Setup & Handoff Guide

This explains, in plain terms, **what the onboarding wizard collects, how it collects
it, and the actions you need to take** (mainly creating the Shopify app in your Partner
account) before it works end-to-end.

For the deeper technical/architecture notes see `ONBOARDING_WIZARD_PLAN.md`.
For deferred decisions see `TO_VISIT_LATER.md`.

---

## 1. The flow at a glance

```
Register & pay (Stripe)  →  Step 1: Connect Shopify  →  Step 2: Branding  →  Dashboard
   (existing)                 (OAuth, built)             (built)              (login)
```

After a successful subscription payment, the success page sends the client into the
wizard via a **signed URL** (no login required yet). They connect Shopify in one click,
confirm branding, and land on the admin login.

---

## 2. What we collect, how, and where it's stored

| Data | How it's collected | Stored on |
|---|---|---|
| Full name, email, password | Registration form (before wizard) | `users` |
| Company name, phone, website | Registration form | `tenants` |
| Plan, billing period, add-ons, country | Registration form + Stripe | `subscriptions` |
| **Shop domain** | **Typed by the client** in Step 1 | `tenants.shopify_shop_domain` |
| **Admin API token** | **Auto** — Shopify OAuth (client approves on Shopify) | `tenants.shopify_admin_token` |
| **Storefront API token** | **Auto** — generated by us after OAuth (`storefrontAccessTokenCreate`) | `tenants.shopify_storefront_token` |
| App name | Step 2, **pre-filled** from Shopify `shop.name` (editable) | `app_configurations.config.basic.app_name` |
| Logo | Step 2, **pre-filled** from Shopify brand assets; client can upload | `app_configurations.config.basic.logo` |
| Primary / secondary colors | Step 2, **pre-filled** from Shopify brand colors (editable) | `app_configurations.config.basic.primary_color` / `secondary_color` |

**Key point:** the only thing the client types about Shopify is the **store URL**.
Everything else (tokens, name, logo, colors) is pulled automatically once they approve
the connection on Shopify. They never copy/paste API keys, and we never see their
Shopify password — they authorize on Shopify's own screen.

> PSP (payment) credentials are **not** collected in the wizard — they are configured
> later in the Payment Gateway admin section.

## 3. What YOU need to do — Shopify Partner app

The whole flow depends on **one** Shopify app that you create once. Its credentials are
shared by all tenants and live in the server `.env` (not per-tenant).

> **Note on where apps live now:** as of Jan 1, 2026 Shopify creates/manages apps in the
> new **Dev Dashboard** (https://dev.shopify.com/dashboard), not the classic Partner
> Dashboard. If your Partner sidebar has no "Apps" item, click **Dev dashboard** at the
> bottom. Steps below use the Dev Dashboard.

### 3.1 Create the app
1. Dev Dashboard → **Apps** → **Create app** → **Start from Dev Dashboard**.
2. Name it (e.g. "Oliv Mobile Apps") → **Create**.

### 3.2 Configure URLs, scopes & install flow (the **Versions** tab)
Config lives under the app's **Versions** tab and **only takes effect when you click
Release** (edits sit in a draft until then).
- ✅ **Use legacy install flow** — **must be checked.** Our backend uses the manual
  authorization-code grant (redirect → `code` → token exchange). Without this, Shopify
  uses managed installation (token exchange) and our `/onboarding/shopify/callback` never
  receives the `code` it expects.
- **App URL:** `https://<your-domain>/admin` (any valid page on your domain).
- **Redirect URLs** (comma-separated): add **exactly**
  ```
  https://<your-domain>/onboarding/shopify/callback
  ```
  Must match our callback route character-for-character (no trailing slash). Add a line
  for each domain you test on (prod, staging, local).
- **Access scopes:** the list in §3.4.
- **API version:** `2025-10`.
- Click **Release**.

### 3.3 Choose distribution
On the app's **Distribution** screen:
- For production, choose **Public distribution** (keep it **unlisted** — no App Store
  listing/review needed; installs on any store via our OAuth link). This matches the
  multi-tenant SaaS model.
- ⚠️ Do **not** pick **Custom distribution** for the production app — it locks to a single
  store. **And the choice is effectively permanent per app** (you can't switch later).
- **An app with no distribution method selected cannot be installed** — hitting the OAuth
  URL returns Shopify's *"Unauthorized Access"* error. Selecting distribution fixes it.
- 💳 Selecting **Public** triggers a **one-time $19 App Store registration fee** for the
  org (then you can make unlimited public apps).
- ❌ **Do not try to avoid the $19 with a Custom-distribution app — it will NOT work with
  our wizard.** See §5c. You need **one Public app** for both local testing and production.

### 3.4 Access scopes
Our app requests these scopes during OAuth (already set in config — see §4). Make sure
the app is allowed to request them:

| Scope | Why |
|---|---|
| `read_products` | Read catalog / collections (for categories step) |
| `read_orders`, `write_orders` | Create & read orders during checkout |
| `write_online_store_navigation` | Create the `flutter-menu` (categories step, later) |
| `unauthenticated_read_product_listings` | Storefront product access for the app |
| `unauthenticated_read_product_inventory` | Storefront inventory |
| `unauthenticated_read_content` | Storefront menus/content |
| `unauthenticated_write_checkouts` | Storefront cart/checkout |

> If you change scopes later, update `SHOPIFY_APP_SCOPES` in `.env` to match, and
> re-connecting stores will re-prompt for the new permissions.

> ⚠️ **`read_orders` / `write_orders` trigger Protected Customer Data (PCD).** Orders
> contain customer PII, so these scopes gate installation until the app is configured for
> PCD — see §5b. For local testing of Steps 1–2 you don't need them; use the minimal
> scope set in §5b.

### 3.5 Copy credentials
From the app's **Settings** tab (Client credentials), copy:
- **Client ID** → `SHOPIFY_APP_CLIENT_ID`
- **Client secret** → `SHOPIFY_APP_CLIENT_SECRET`

### 3.6 Local testing — one Public app + Expose (NOT a free Custom app)

> ⚠️ **Correction from hard-won experience:** Custom distribution is **free but does NOT
> work with our wizard** (see §5c — Custom only supports the managed-install link, which
> never hits our callback). So there is **no free shortcut**. Use **one Public app**
> (unlisted, $19 one-time) for **both** local testing and production.

For **local testing**, the only extra requirement is a **public redirect URI** (Shopify
rejects local `.test` domains). Get one with **Expose** via Herd:

1. Herd → **Expose** pane → paste your free Expose token (no `composer` needed — Herd
   bundles Expose).
2. `cd ~/Herd/oliv && herd share` → gives `https://<random>.sharedwithexpose.com`. **Keep
   it running.**
3. `.env` → `APP_URL=https://<random>.sharedwithexpose.com`
4. Public app → Redirect URLs → add `https://<random>.sharedwithexpose.com/onboarding/shopify/callback`
   → **Release**.
5. `php artisan config:clear`, open the wizard at the **Expose URL** and test.

⚠️ Free Expose subdomains **rotate on every restart** — keep the session up, or redo steps
3–5 with the new subdomain.

The remainder below (the two-app split) is **deprecated** — kept only to explain why the
Custom route fails. **Skip it; use one Public app.**

<details><summary>Deprecated: the old "Custom test app" approach (does not work)</summary>

1. Create a **second app** → choose **Custom distribution** (free) → set its allowed store
   to your development store.
2. Give it the **same** Redirect URLs + scopes + **Use legacy install flow**, then Release.
3. Put **that app's** Client ID/secret in your **local `.env`** and test the full

4. Keep the Public app for production and pay the $19 only when going live.

## 4. Environment variables (server `.env`)

```env
SHOPIFY_APP_CLIENT_ID=your_client_id
SHOPIFY_APP_CLIENT_SECRET=your_client_secret
SHOPIFY_API_VERSION=2025-10
SHOPIFY_APP_SCOPES="read_products,read_orders,write_orders,write_online_store_navigation,unauthenticated_read_product_listings,unauthenticated_read_product_inventory,unauthenticated_read_content,unauthenticated_write_checkouts"
```

After editing `.env` in production, run `php artisan config:clear` (and `config:cache` if
you cache config).

## 5. How to test it

1. Set the env vars above with your real app credentials.
2. Have a **development store** in your Partner account to install onto.
3. Go through registration + a (test-mode) Stripe payment, or build a signed Step-1 URL
   for an existing tenant.
4. On Step 1, enter the dev store domain → you should be redirected to Shopify's consent
   screen → approve → you return to Step 2 with the store connected.
5. Confirm on the tenant record that `shopify_admin_token` and
   `shopify_storefront_token` are now populated, and Step 2 shows the store's name /
   brand colors if the store has brand assets set.

## 5a. Troubleshooting

**Shopify shows "Oops, something went wrong — Unauthorized Access" on the consent screen.**
Two common causes:
1. **No distribution method selected** on the app (Overview → Distribution says "Select
   distribution method"). An app with no distribution can't be installed. Fix: §3.3.
2. **`redirect_uri` mismatch.** The `redirect_uri` in the authorize URL must exactly match
   a whitelisted Redirect URL. Our app generates it from `APP_URL`, so if you test on
   `oliv.test` locally, `APP_URL` must be `https://oliv.test` **and** that exact callback
   must be in the app's Redirect URLs. Also remember Dev Dashboard config only applies
   **after Release**.

**Config changes seem to have no effect.** In the Dev Dashboard, edits live in a draft
until you click **Release** and that version shows **Active**.

**"The installation link for this app is invalid."** Usually a **scope mismatch**: our
wizard builds the OAuth request from `.env` `SHOPIFY_APP_SCOPES`, and if that asks for
**more scopes than the app declares** (Dev Dashboard, released), Shopify rejects it as
invalid. Fix: make `SHOPIFY_APP_SCOPES` exactly match the app's released scopes, then
`php artisan config:clear`. (It is *not* caused by the custom install link here — always
start from the wizard anyway, never that link.)

> 🔑 **Scopes live in two places and must match:** the **Dev Dashboard** (released) **and**
> `.env` `SHOPIFY_APP_SCOPES`. Change one → change both → Release + `config:clear`.

## 5b. The "Install" button is grayed out — Protected Customer Data (PCD)

**Symptom:** you reach Shopify's consent screen, it lists *"View customer data — Sensitive
data…"*, but the **Install** button is disabled.

**Cause:** the app requests **`read_orders` / `write_orders`**. Orders contain customer
PII, which Shopify classifies as **Protected Customer Data**. Apps requesting those scopes
**cannot be installed until configured/approved for PCD**.

**Important gap:** the new **Dev Dashboard currently has no UI to request PCD for *custom*
apps** (community-reported). So on the **Custom test app** you usually **can't** complete
the PCD form at all. (PCD *is* available for **Public** apps via the Partner Dashboard
data-protection flow — and dev/test installs don't need Shopify review, only the
declaration.)

> The "API access requests" page in the legacy Partner Dashboard (full order history,
> subscriptions, payment mandates, …) is **not** the PCD setting — those are unrelated
> optional scopes.

### Fix for local testing — trim to the minimal scope set
Steps 1–2 (OAuth, storefront token, branding) don't need order scopes. Use:

```
read_products,write_online_store_navigation,unauthenticated_read_product_listings,unauthenticated_read_product_inventory,unauthenticated_read_content
```

(Dropped: `read_orders`, `write_orders`, `unauthenticated_write_checkouts`.)

Apply in **both** places, then reinstall:
1. Dev Dashboard → app scopes → set to the list above → **Release**.
2. Local `.env` → `SHOPIFY_APP_SCOPES="…list above…"` → `php artisan config:clear`.
3. Retry Step 1 → Install is now enabled → approve → tokens saved → Step 2.

### For production
On the **Public** app, add `read_orders` / `write_orders` back and complete the **Protected
Customer Data** declaration in the Partner Dashboard before you need order creation /
checkout. Order/checkout features are not part of onboarding Steps 1–2, so nothing is lost
by deferring this.

Refs: [Work with protected customer data](https://shopify.dev/docs/apps/launch/protected-customer-data),
[Dev Dashboard PCD gap (community)](https://community.shopify.dev/t/enable-protected-customer-data-access-for-a-custom-app-created-in-the-dev-dashboard-no-ui-option-available/35445)

## 5c. ⭐ Custom distribution CANNOT drive our wizard — use Public distribution

**This is the single most important lesson from the first setup.** If "installation link is
invalid" persists after you've fixed redirect URI, scopes, client_id, embedded, and store —
the cause is the **distribution type**.

**Why:** our onboarding wizard installs the app via a **standalone OAuth authorize URL**
(`/admin/oauth/authorize?…&redirect_uri=…/onboarding/shopify/callback`). A **Custom-
distribution** app does **not** support that — it can only be installed through its **custom
install link**, which performs a **managed install** and lands the merchant on the app's
**App URL**, *never* on our `redirect_uri`. So a Custom app can **never** hand our backend
the `code` it needs. You'll get `…/app/grant?access_change_uuid=…` → "installation link is
invalid," no matter how perfectly everything else is configured.

**Confirmed empirically** during first setup: with a public Expose redirect URI, matching
scopes, matching client_id, `embedded:false`, correct bound store, and a fresh private
window — a Custom app still failed. Switching to **Public distribution** fixed it.

**Rule of thumb:**
- **Public distribution** → standalone OAuth authorize URL works → our wizard works. ✅
  (This is also the production model. Requires the one-time **$19** App Store registration;
  can stay **unlisted**.)
- **Custom distribution** → install-link / managed-install only → **incompatible with our
  wizard.** ❌ Don't use it for this app.

**For local testing** you still need a **public redirect URI** (Shopify rejects local
`.test` domains). Use **Expose** (`herd share`) to get a public
`https://<random>.sharedwithexpose.com` URL; put it in `.env` `APP_URL` and in the app's
Redirect URLs. ⚠️ On the free plan the subdomain **rotates every restart** — keep one
`herd share` session running, or re-update `APP_URL` + Redirect URL + `config:clear` each time.

> Net: **one Public app** (unlisted, $19) for both local testing (via Expose) and
> production. Skip Custom distribution entirely for the onboarding integration.

Refs: [Custom distribution "invalid link" cause (community)](https://community.shopify.com/c/shopify-apps/the-installation-link-for-this-app-is-invalid/m-p/2476079),
[Authorization code grant](https://shopify.dev/docs/apps/build/authentication-authorization/access-tokens/authorization-code-grant)

## 6. Things to be aware of / decisions still open

- **Brand assets may be empty.** Logo/colors only pre-fill if the merchant filled in
  *Shopify → Settings → Brand*. Otherwise Step 2 falls back to editable defaults — this
  is expected, not a bug.
- **Storefront token is required.** If we can't mint it after OAuth, the client stays on
  Step 1 with a notice and your team finishes it manually. (Usually means a missing
  `unauthenticated_*` scope.)
- **Categories & store-info steps** are not built yet; after branding the client is sent
  to the dashboard login.
- **Legacy fields.** Old per-tenant `shopify_client_id` / `shopify_client_secret` columns
  still exist from the previous manual model and can be removed once fully retired.
- **OneSignal & app-build identifiers** are out of scope for now — see `TO_VISIT_LATER.md`.
